# ADR-007-employer-accounts-and-secure-access

## Status
Proposed

## Context
UC-003 adds separate accounts and employer-owned payroll data to one PayAlign deployment. The current application assumes one global employer: setup reads the first employer, employee AHV is globally unique, and payroll repository methods accept record identifiers without an authenticated owner's scope. `create_schema()` creates the schema for a new database. The application is composed in `create_app()` and follows the inward dependency direction in [ADR-001](ADR-001-clean-architecture-boundaries.md).

Account access changes the trust boundary and persistence model, but payroll calculations and their domain rules do not depend on identity. UC-003 assumes a fresh database with no pre-account employer or payroll data; the first account is created by registration from the login page.

The relevant login-instance failure is process-global authenticated state: a module-level current-user value is shared between browser connections, so one browser's login can overwrite another browser's identity. Each browser must instead carry independent session state, and each protected request must resolve its account from that session and reload the account from persistence. No authenticated identity may be stored in a process-global current-user value.

## Alternatives
- Put username and password fields on `Employer`: not chosen, because login identity and employer legal/contact details have different lifecycles, and credential handling should be isolated from the payroll entity.
- Keep one deployment-wide configured password: not chosen, because it cannot isolate multiple employers' records.
- Let each router perform ownership checks independently: not chosen, because checks can be omitted and access policy would be duplicated.
- Keep employees globally unique by AHV number: not chosen, because the shared employee row would disclose or overwrite one employer's details when another employer employs the same person.

## Decision
These are proposed design choices for human review; none is recorded as accepted. Session storage and the post-login browser flow remain open pending the answers below.

1. **Account and employer ownership.** `Account` is the login identity, not a superclass or subtype of `Employer`. Add an `accounts` table with `id` (database-generated primary key), unique normalized `email`, `password_hash`, `first_name` and `last_name`. Keep those personal/login fields separate from the employer's legal profile. Add a required `employers.account_id` foreign key to `accounts.id` with a unique constraint. This means every employer belongs to exactly one account and an account can have at most one employer. An account may temporarily have no employer while onboarding; its first setup creates the separate employer row, whose `employers.id` is generated by the database. The account-to-employer relationship is therefore one-to-zero-or-one during onboarding, and one-to-one after employer setup. The client does not choose either generated ID.
2. **Layer boundaries.** Keep payroll domain entities and calculations independent of authentication. Add an account use-case service plus account repository and password-hasher ports in Application. Interfaces provide registration, login, logout and a request dependency that resolves a trusted account principal from the browser session. `create_app()` composes the account service and adapters and configures Starlette's session middleware. Infrastructure owns the password-hasher adapter, ORM mappings and migrations. No router imports an infrastructure adapter.
3. **Browser workflows.** The browser experience includes login and registration, employer setup, employee/employment setup, and monthly payroll entry. These pages expose the existing setup and payroll fields through the web interface; Swagger remains a developer API tool, not the employer workflow. The post-registration onboarding sequence remains open. The chosen session mechanism must keep browser sessions independent, load the account from persistence on each protected request, and never accept an employer ID from the browser as identity authority. Never put a password, password hash or full account object in a session cookie. Protect state-changing cookie-authenticated requests against CSRF.
4. **Ownership enforcement.** Resolve the account's employer once per request and pass that trusted ownership context through application services to repository ports. Every setup, employee, employment, monthly-record and payslip lookup or write that is reached by caller-supplied IDs must include the resolved employer scope in its query or write precondition. Return the same not-found outcome for absent and out-of-scope record IDs. Keep `/health` public and free of employer data.
5. **Employer-scoped employee identity.** Store employee identity under an employer and enforce AHV uniqueness within that employer, rather than globally. Do not reuse an employee row across employers. Enforce that an employment's employer matches the employer-scoped employee, and keep payroll record ownership consistent with its employment.
6. **Fresh install and onboarding.** UC-003 assumes the initial database has no employer or payroll records. Registration creates the first account; account and employer data remain separate, and the database generates the employer ID when an employer profile is created. Whether initial setup should use the existing UC-001 flow or a separate employer-profile step remains open. This fresh-install assumption does not define a migration or bootstrap process for a database that already contains records.
7. **Credential policy.** Store only an adaptive password hash using a maintained password-hashing library. Never log passwords, hashes or session tokens. Password reset, email verification, invitations, multiple accounts per employer, account deletion and employer transfer remain outside UC-003.

The intended persistence relationship is:

```text
accounts
  id                 INTEGER PRIMARY KEY (database-generated)
  email              TEXT NOT NULL UNIQUE (normalized before storage)
  password_hash      TEXT NOT NULL
  first_name         TEXT NOT NULL
  last_name          TEXT NOT NULL

employers
  id                 INTEGER PRIMARY KEY (database-generated)
  account_id         INTEGER NOT NULL UNIQUE REFERENCES accounts(id)
  name, address, ahv_number, contact_info  existing employer profile fields
```

`Account` does not inherit employer fields and `Employer` does not contain credentials. The account ID identifies who may access the profile; the employer ID continues to identify the employer record used by setup, employment and payroll data.

The proposed application-facing boundaries are:
- `AccountService`: register accounts and verify submitted credentials using the account repository and password-hasher ports.
- `AccountRepository` and `PasswordHasher`: application ports implemented by infrastructure adapters.
- A session mechanism: provides independent browser state; login/logout routes establish or end that session (mechanism pending the human decision below).
- `AuthenticatedAccount` (or equivalent): trusted principal loaded from the account ID in the validated session; passed to setup and payroll application operations as ownership context.
- Existing setup and payroll repository ports: become explicitly employer-scoped; adapters enforce ownership in database operations.

No payroll formula, rate, rounding rule or calculation input changes as part of this decision.

## Consequences
- The interface cannot choose an account or employer by request payload; identity comes from a validated session and scope is enforced again in persistence access.
- Setup, employee identity and payroll ports/adapters need coordinated changes. Payroll service calculations remain unchanged, but employment and historical-run reads must be scoped.
- Registration creates an account. First-time setup creates the associated employer row and receives its database-generated employer ID; the employer profile is not implicitly populated from the account's first and last name.
- The session mechanism and lifetime determine the balance between implementation size and per-session revocation. A signed cookie avoids a session table but a copied cookie cannot be revoked individually before expiry; a server-side session record adds persistence and supports immediate revocation.
- New account and employer tables are created together for the fresh database. No existing-data migration or operator bootstrap is needed for this initial rollout.
- Same-AHV employees can be represented separately for separate employers; this duplicates personal data but prevents cross-employer reads and edits.
- On human acceptance, update `docs/PROJECT.md` in the implementation change to describe the account boundary, authentication endpoints, ownership model and browser workflows. No `AGENTS.md` rule change is proposed.
- The initial setup/browser flow and session/revocation choices must be answered before this ADR can be accepted.

## Supersedes
none

## Open questions
- UC-001 currently gathers employer details together with the first employee and employment. Should that remain one onboarding flow after registration, or should employer-profile creation be a separate page/step before employee and employment setup?
- Which session behavior is required: a signed cookie ending when the browser closes, a signed cookie with a fixed expiry, or a server-side session that supports immediate revocation?
