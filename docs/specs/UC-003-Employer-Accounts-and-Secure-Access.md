# UC-003: Employer Accounts and Secure Access

Last updated: 2026-10-24

## Goal
Let multiple household employers use one PayAlign deployment with separate accounts and isolated payroll data.

## Business value
Household employers can securely manage their own employment and payroll records on the shared PayAlign service.

## Scope

### In scope
- Create an account with a unique email login, password and first and last name through a basic registration interface.
- Store a password hash, never a plaintext password.
- Log in and out through a basic browser interface with a session isolated from other users.
- Associate at most one employer profile with each account. Registration creates the login account; first-time setup creates its separate employer profile, with the employer ID generated by persistence. The employer's legal and contact details remain the fields defined by UC-001 and are not inferred from the account's first and last name.
- Require authentication for setup, employer and monthly payroll operations.
- Scope setup, employee lookups, employment access, payroll history and payslips to the signed-in account's employer.
- Keep employee details employer-scoped; the same AHV number may have separate records for different employers, without sharing profile details.

### Out of scope
- Multiple accounts, roles or invitations for one employer.
- Password reset, email verification and external identity providers.
- Account deletion and employer transfer.
- Migration or recovery of pre-account employer/payroll data; this feature starts with a new, empty database.
- Payroll calculation or legal-rule changes.

## Actors
**Primary:** Household employer.

**Secondary:** PayAlign.

## Preconditions
- PayAlign and its relational database are available.
- The employer has an account, or can create one.

## Trigger
The employer registers or logs in to manage employment and payroll data.

## Main flow
1. A visitor opens PayAlign and sees the login page, which provides account registration and login.
2. A new employer registers using a unique email, password and first and last name. PayAlign stores a password hash and signs that browser in. A returning employer logs in with the existing account.
3. The employer completes first-time employer setup under UC-001. PayAlign creates a separate employer profile linked to the account and generates the employer ID; the visitor cannot choose either ID.
4. For each protected operation, PayAlign resolves the employer owned by the account authenticated in that browser's session and limits access to that employer's records.
5. The employer logs out; that browser's session no longer grants access.

## Alternate / edge flows
- A registered account without an employer profile is directed to complete setup; it cannot process payroll until setup creates its associated employer profile.
- A second account can use the service concurrently without changing the first account's identity or access.
- An employee with the same AHV number at another employer is treated as a separate employer-scoped record.

## Errors / failure cases
- Duplicate account email is rejected.
- Invalid login returns a generic authentication error.
- Protected requests without a valid session are rejected.
- Requests for another employer's employment, employee, payroll run or payslip are denied without revealing whether the record exists.
- Persistence error handling follows [UC-002 acceptance criteria](UC-002-Process-the-Monthly-Employment.md#acceptance-criteria) and [ADR-005's persistence error decision](../adr/ADR-005-sqlalchemy-persistence-adapter.md#decision).

## Acceptance criteria
- Given two accounts logged in from separate browser sessions, when both use PayAlign concurrently, each request uses only the employer belonging to the account logged in through that browser; neither user's identity overwrites the other's.
- Given a missing, invalid or expired session, when it calls a protected operation, then the request is rejected.
- Given an account that logs out, when that browser next calls a protected operation, then the request is rejected.
- Given a new installation, when a visitor opens PayAlign, then the login/registration page is the entry page and registration can create the first account without operator pre-provisioning.
- Given an account, when its password is saved, then only a password hash is persisted.
- Given an unauthenticated request, when it calls a protected setup or payroll operation, then the operation is rejected.
- Given an account and another employer's employment ID, when payroll is requested, then no data is read or written for that employment.
- Given an account, when it accesses its employer's setup and payroll records, then those operations continue to work.
- Given an employee with the same AHV number at two employers, when each employer manages that employee, then neither can read or overwrite the other's employee details.
- Given the registration, login and logout interface, when an employer uses it, then the resulting session grants only that account access and logout ends that access.

## Security / trust-boundary notes
- The authenticated account ID comes from a server-validated session; clients cannot choose an account or employer ID to gain access.
- Each browser must have independent session state. For every protected request, PayAlign must resolve the authenticated account from that browser's session and load the account from persistence; it must never use a process-global current-account value shared across browser connections. Session credentials must be protected from tampering and must not expose passwords or password hashes. Require an adaptive password hash and protect state-changing requests against cross-site request forgery. Session duration, cookie settings and implementation mechanism are design decisions.
- Apply ownership checks in application/repository access paths, not only in the UI.
- Protect state-changing cookie-authenticated requests against CSRF.
- Keep health monitoring available without exposing employer data.

## Validation plan

### Tests
- Unit: account validation, password verification and authorization for employer-scoped operations.
- Integration: registration, login, logout, protected endpoints and employer-scoped queries against the newly created database schema.
- End-to-end: two independent browser clients remain isolated through setup and payroll, including attempts to use each other's record IDs.

### Evidence
At VALIDATE, record the actual test results in the commit message.

## Open questions / assumptions
- Assumption: each account is the login identity for one household employer. During onboarding an account may have no employer profile; after successful first-time setup it has exactly one. Each employer profile belongs to exactly one account. `Account` and `Employer` are separate entities in a one-to-one relationship, not an inheritance hierarchy.
- Assumption: email is the unique login identifier, and account first and last names are distinct from the employer's legal name and contact details.
- Assumption: the initial deployment has no existing database or employer/payroll data. The login page offers registration from first startup, so the first account is created through the same registration flow as later accounts.

## Notes for implementation
- Keep payroll calculation rules independent from accounts. The interfaces layer owns the registration/login/logout routes and basic browser UI; resolve the authenticated account at that boundary and pass trusted ownership context through application ports to persistence.
- The employer linked to the account scopes its employments; repository queries must include that ownership scope even when a caller supplies an employment ID.
- Replace the global employee AHV lookup with employer-scoped employee identity and uniqueness.
- Likely affected areas: src/app/interfaces/, src/app/application/, src/app/application/ports/, src/app/infrastructure/orm_models.py, SQLAlchemy repositories, app wiring, database schema, and integration/end-to-end tests.

## Amendment 1 — 2026-10-23: Browser workflows and session lifetime
- Add browser pages for employer setup, employee/employment setup and monthly payroll entry. They expose the fields and follow the behavior already defined by UC-001 and UC-002; Swagger remains a developer tool, not the employer workflow.
- First-time onboarding presents employer details before the first employee and employment details, then submits them together through the setup operation.
- A login session has a fixed four-hour lifetime from successful login. After expiry, the employer must log in again. There is no inactivity-based timeout in this slice. Session implementation and the known limitation that a copied cookie remains usable until expiry are specified in ADR-007.
- Given a registered employer, when they complete setup and process payroll, then both workflows are available through browser pages using the UC-001 and UC-002 fields and rules.

## Amendment 2 — 2026-10-23: Explicit session and CSRF behavior
- This amendment resolves the earlier statement under Security / trust-boundary notes that session duration and cookie settings remained design decisions. Use Starlette `SessionMiddleware` as selected in [ADR-007 Amendment 1](../adr/ADR-007-employer-accounts-and-secure-access.md#amendment-1--2026-10-23-explicit-session-and-csrf-protocol).
- A session contains only the account ID, expires four hours after successful registration or login, and is not extended by ordinary requests. Use an HttpOnly, SameSite=Lax cookie and Secure over HTTPS. Logout clears the current browser's cookie; it does not revoke copied cookies before their original expiry.
- The browser obtains a random CSRF token from `GET /api/v1/auth/csrf`. PayAlign sets the token in a separate browser-readable `csrf_token` cookie and returns it to the UI. The UI sends the same token in `X-CSRF-Token` on every state-changing cookie-authenticated request, including registration, login, logout, setup and payroll writes. The CSRF token carries no identity authority and is not a signed session credential.
- Given a missing or non-matching CSRF cookie/header pair, when a state-changing cookie-authenticated request is made, then PayAlign rejects it before performing the operation, comparing the values in constant time.
- Given ordinary authenticated requests before session expiry, when they occur, then the session expiry is not extended.
- [Amendment 4](#amendment-4--2026-10-24-registration-policy-and-csrf-token-return) clarifies the token returned after authentication and malformed-token handling.

## Amendment 3 — 2026-10-23: Minimum browser views

The requesting human defined these five view boundaries on 2026-10-23 to identify the logic the application must provide. The UI implementation chooses presentation, navigation details and the data each view needs within the behavior owned by [UC-001](UC-001-Set-Up-an-Employment.md), [UC-002](UC-002-Process-the-Monthly-Employment.md) and this use case. The logic stays available through account-scoped application interfaces rather than being tied to one page layout.

| View | Required capability |
|---|---|
| 0 — Login | Register, log in, log out and resolve the current account. |
| 1 — Setup | Create the employer profile and first employee/employment as in UC-001; add later employments under the same employer. |
| 2 — Employments | List the signed-in employer's employments and select one. |
| 3 — Employment months | Read one owned employment's completed months and their saved payslips; identify the next month allowed by UC-002. Completed months are view-only. |
| 4 — Month entry | Create the next monthly run with the UC-002 inputs and show its resulting payslip. |

The month-entry view submits a month's entries together for processing. Saving unfinished entries weekly as a persistent draft is outside this use case and may be developed later.

The CRUD boundary is explicit: account and employer creation, setup creation, and monthly-run creation are supported by the cited use cases; owned employer, employment, month and payslip reads are required for these views. [UC-001](UC-001-Set-Up-an-Employment.md#scope) excludes changing or ending an employment after setup, and its saved employee details are reused rather than overwritten. [UC-002](UC-002-Process-the-Monthly-Employment.md#scope) excludes corrections and reversals of completed months. [UC-003](#scope) excludes account deletion and employer transfer. These views do not add update or delete operations contrary to those boundaries; any future edit/delete behavior needs its own use-case decision.

All list and detail reads must use the signed-in account's employer scope. An absent or another employer's employment, month or payslip has the same not-found outcome. The browser view itself grants no authority; application and repository checks remain required by [ADR-007](../adr/ADR-007-employer-accounts-and-secure-access.md#decision).

Acceptance: Two concurrent accounts see only their own employment lists, months and payslips. A new account can complete setup, find its employment, create its first eligible month and read its saved payslip without Swagger. A completed month remains readable and has no update or delete action.

## Amendment 4 — 2026-10-24: Registration policy and CSRF token return

Guin-Kiwi selected the registration password policy on 2026-10-24: at least
[the configured minimum length](../../src/app/domain/constants.py), including at
least one decimal digit and one special character. A special character is a
non-alphanumeric, non-whitespace character. Longer passwords and Unicode are
allowed; there is no uppercase/lowercase requirement. Validate before hashing or
saving an account. Login verifies the saved hash without applying the registration
policy again.

Successful registration and login rotate the CSRF cookie and return its new value
as `csrf_token` alongside the account fields in the JSON response. The browser
uses that value on its next state-changing request without another token fetch.
The previous token is rejected. `GET /api/v1/auth/me` continues to return only the
account fields. Non-ASCII CSRF cookie or header values are malformed and return
403 without starting or changing a session.

Validation: `tests/integration/test_auth_api.py` covers immediate authenticated
setup after registration/login, stale-token rejection, malformed tokens and
rejected registrations without persistence. `tests/unit/test_account_service.py`
covers password validation at the application boundary and preservation of
valid long and Unicode passwords.
